# lab4｜用负载矩阵区分吞吐与延迟

[索引](../guides/course-map.md) · [对应课程 lab4](../modules/lab4-scheduling.md) · [前置 lab3](lab3-serving.md)

> [!tip] AI 辅助增强

## 要回答的问题

在同一服务配置下，输入长度和到达率分别怎样影响 TTFT、TPOT、输出吞吐和 SLO 满足率？本实验建立负载意识，尚不改变服务算法。需要 lab3 已通过，继续使用其模型、配置、版本和分析脚本。

参考：[vLLM benchmark CLI](https://docs.vllm.ai/en/stable/cli/bench/serve/)、[DistServe](https://arxiv.org/abs/2401.09670)、[指标规范](../guides/experiments.md)。随机输入是容量/调度实验，不代表真实语义任务或生成质量评估。

## 固定运行矩阵

从 lab3 的 `calibration.json` 读取 C。设 `λ_low=0.3C`、`λ_high=0.7C`，单位 req/s，计算成明确数字写入配置。比如 C=4 时是 1.2 与 2.8；这只是算术示例，必须代入你的实测值。

| 条件 | 目标输入 token | 输出 token | 到达率 | 重复/seed |
|---|---:|---:|---|---|
| short-low | 128 | 64 | 0.3C | 11 / 22 / 33 |
| short-high | 128 | 64 | 0.7C | 11 / 22 / 33 |
| long-low | 1024 | 64 | 0.3C | 11 / 22 / 33 |
| long-high | 1024 | 64 | 0.7C | 11 / 22 / 33 |

共 12 次正式运行。Poisson 到达用 `burstiness=1`；`random-range-ratio=0`（须核对版本语义）；ignore_eos 开启，prefix caching 关闭。有限到达率实验不加客户端 max-concurrency 限制，否则客户端排队会改变实际到达。服务端仍保留 max-num-seqs=4。

默认每轮 N=120。若 pilot 显示运行太短，可统一采用 `N=max(120,ceil(20*λ_high))`，最多先取 600；将 N 在正式运行前固定，各条件一致。达到上限仍不足约 20 秒时标注短时测量局限。若按 C 估计整个矩阵需超过 100 分钟，可统一退到 N=60 并标注尾部估计很粗；仍超时就顺延，不删掉表现不好的条件。

## 运行前 pilot 与 SLO

先用长输入、λ_low、30 个请求做 pilot，不计入正式结果。以该 pilot 的请求级 TTFT 和 TPOT 中位数分别乘 2，得到教学目标 `T_ttft`、`T_tpot`，换算成毫秒后写入 `slo.json`，之后所有条件保持不变。这是为了练习目标约束下的评估，不是假定真实用户就接受这个延迟。

如果 pilot 有失败、长度异常或服务未预热，先修复再确定 SLO。正式测量后不得为提高满足率再放宽阈值。若所有请求都满足或都不满足，也保留该结果，并在下一轮设计中讨论目标是否有区分度。

## 如何执行 12 次运行

复用 lab3 的完整 benchmark 命令，每次只替换 `--random-input-len`、`--request-rate`、`--num-prompts`、`--seed`、文件名；显式添加 `--burstiness 1`。例如在“C=4 的示例”中 short-low 使用输入 128、rate 1.2，实际操作时用自己的数值。

建立 `run_matrix.csv`，字段为 `run_id,input_len,output_len,request_rate,burstiness,num_prompts,seed`。每个 seed 内交错短/长和低/高条件，下一轮反向或事先随机打乱，保存顺序。全部串行完成，前一轮排空才开始下一轮。每次重启服务器后预热，但不因为结果差就随意重启某一条件。

相同 seed 有助复查，但不保证不同输入长度下产生完全相同的实际到达时间序列。本课程比较相同到达分布与设定参数；只有保存并重放时间戳 trace 后，才声称“逐请求相同到达”。

## 分析步骤

1. 对每轮检查请求数、成功数、失败数、目标/实际长度、持续时间。失败和超时不能从表中消失。
2. 输出吞吐用总实际输出 token / 测量时段；p50/p95 TTFT 与 TPOT 使用请求级明细或已核对定义的工具汇总。
3. 对每个请求判断是否成功且同时满足两个 SLO。满足率分母为 N，goodput 为满足请求数 / 时段长度。若工具明细不足以重算，明确记录缺失字段并补保存配置，不用平均值冒充满足率。
4. 画图 A：横轴到达率，纵轴 p95 TTFT，按输入长度分线，每轮一个点并展示范围。图 B：输出吞吐与 SLO 满足率并列展示，不共用模糊的纵轴。
5. 写四句结论：观察、机制解释、限制、下一步最小检查。p95 基于有限样本，只作探索性判断；不宣称统计显著。

## 交付与验收

交付：预注册记录、`run_matrix.csv`、`slo.json`、12 份原始结果与命令、逐轮汇总、分析脚本、两张图、600–900 字报告。

- [ ] 同一模型、版本、调度与缓存配置贯穿所有条件。
- [ ] 两个到达率是数值明确的有限 rate，没有误用 inf。
- [ ] 每条件三轮；没有只保留最好一轮或把失败丢掉。
- [ ] SLO 在正式测量前固定，满足率可以追溯到请求级数据。
- [ ] 能解释“提高到达率”不等于“成功吞吐等比例提高”。
- [ ] 区分了总 TTFT 与纯 prefill 计算，未凭一张总延迟图断言内部原因。

## 卡点与选做

若队列无法在合理时间排空或大量超时，停止当前轮、保存日志，清理自己启动的未完成请求/服务后重新预热。可将**整组**到达率降低后重跑，并保留原过载数据作为另一轮实验；不能只降低困难条件的负载再横向比较。

选做（不计入 5h）：用工具支持的 custom/timed trace 数据格式设计 50% 短＋50% 长的混合负载，并明确保存到达时间与实际 token 长度。不要直接将两次独立 benchmark 同时启动后声称得到精确混合 trace。
